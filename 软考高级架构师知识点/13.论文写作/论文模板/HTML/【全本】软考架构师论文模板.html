五、三条写作心法

  1. 写决策，不写名词 ❌「系统采用了微服务架构，使用了 Docker 和 Kubernetes」 ✅「考虑到预约、消息、批处理的伸缩特征差异巨大（预约是突发流量、批处理是定时峰值、 消息是持续低频），我把它们拆分为独立部署单元，使批处理的资源峰值不再影响在线预约接口」

  2. 写权衡，不写完美 ❌「我们选择了最优方案」 ✅「该方案牺牲了跨表事务一致性，换来弹性伸缩能力；考虑到旅游预约场景下 跨域事务极少，这个交换是可接受的」

  3. 写演化，不写一步到位 ❌「系统一开始就是现在这个架构」 ✅「初期采用单体部署，随着【业务变化】，暴露出【问题】， 我们在【阶段】进行了【拆分/重构】，其中【难点】通过【手段】解决」

  2. 在剩下 3 题里找能塞进你素材库难点最多的那道

四、难点素材库（论文「难点与解决」段的核心弹药）

每个难点都已标注可套用的主题。考场上优先选与你题目最贴合的 2～3 个。

① 一份 proto 契约驱动三语言客户端

  • 问题：系统需同时为 Java（内部服务）、Go（周边平台）、PHP（既有遗留系统）提供 API。 若各自维护接口定义，字段口径必然漂移，联调成本高，回归风险大。
  • 方案：在 base-home-spec 中以 protobuf 作为唯一契约源， 通过 build.sh 编排 build-java → build-go → build-php → generate-all， 分别用 protoc-gen-grpc-java、protoc --go_out/--go-grpc_out/--grpc-gateway_out、 --php_out + grpc_php_plugin 生成三语言产物并独立发布（Maven / Go module / Composer）。 同时用 --openapiv2_out 产出 base_home_api.swagger.json，经 MkDocs 发布为在线文档。
  • 可量化效果：一份契约、17 个 RPC 三端一致；接口变更由构建流水线统一验证， 消除了人工同步定义；base-home-spec 产出的 90 个 proto 文件全部纳入版本管理。 🔶 建议补充：改造前后接口联调耗时对比、字段不一致缺陷数下降比例。
  • 可套用主题：系统集成、微服务、架构复用、架构演化

② protobuf 依赖版本冲突导致服务启动失败

  • 问题：proto-google-common-protos 升到 2.64.0-rc1 后，gRPC 服务启动报错， 且因版本区间声明为 [3,4)、grpcVersion = latest.release，故障在构建期不显现， 只在运行时暴露，属于典型的依赖漂移引发的架构风险。
  • 方案：在 base-home-versions 的统一版本源中， 通过 resolutionStrategy { force ... } 将 proto-google-common-protos 锁定到 2.63.2， 并同步锁定 MyBatis 3.0.5 等关键组件，把「隐式版本」变成「显式契约」。
  • 可量化效果：启动失败问题消除；构建可复现（同一 commit 任意机器产物一致）。 🔶 建议补充：锁定前每月因依赖漂移导致的构建/启动故障次数。
  • 可套用主题：微服务治理、架构可维护性、架构演化、CI/CD（本难点非常适合"架构可维护性/演化"类题目，因为它体现"架构决策的长期成本"）

③ AWS SDK v1 与 v2 长期并存

  • 问题：项目历史遗留使用 AWS SDK v1（S3 / STS）， 而 DynamoDB 增强客户端（DynamoDbEnhancedClient）只在 v2 提供， 两套 SDK 的凭证链、异常模型、配置方式完全不同，直接替换会波及大量既有代码。
  • 方案：接受双版本并存的过渡态，按能力边界划分： 新增能力（DynamoDB 增强访问、STS AssumeRole）一律走 v2， 既有能力暂留 v1；在 DynamoDbConfig / AwsConfig 中集中封装客户端构建， 统一注入 STS AssumeRole 临时凭证 + DefaultCredentialsProvider 兜底。
  • 可量化效果：新功能不再受阻于 SDK 版本；凭证获取统一收口到配置类，一账户一集群。 🔶 建议补充：统一凭证后的凭证失效类故障下降情况。
  • 可套用主题：架构演化、遗留系统改造、系统集成（这是"不追求一次性重写、渐进式演进"的绝佳论据）

④ MySQL 读写分离双数据源

  • 问题：批处理既要从生产库大量读取（成本文件、ToDo、预约导入）， 又要回写结果，读写互相争抢资源，长事务影响在线业务。
  • 方案：在 base-home-batch 中配置双数据源： ReaderDataSourceConfig（spring.datasource.reader）与 WriterDataSourceConfig（spring.datasource.writer，标 @Primary）， 通过包路径隔离 Mapper（repository/reader/ 与 repository/writer/）， 事务隔离级别设为 TRANSACTION_READ_COMMITTED，defaultFetchSize=200 控制批量游标。
  • 可量化效果：读写物理隔离，批量作业不再挤占在线库连接池。 🔶 建议补充：作业耗时、在线接口 P99 响应时间的改善数据。
  • 可套用主题：数据架构、批处理、高可用、性能优化

⑤ DynamoDB 单表多实体 + 混合存储的数据架构

  • 问题：旅游业务数据形态差异极大—— 旅行主数据（Travel）字段频繁演进、文档（Document）为二进制引用、 消息线程（MessageThread）读写频繁、序列号（Sequence）要求强一致自增。 若全部塞进关系库，扩展性与弹性不足；若全部 NoSQL，又丢失事务与关联查询能力。
  • 方案：混合存储（Polyglot Persistence）：
  • 关系型（Aurora MySQL）承载交易强一致与复杂查询（53 张 T* 业务表 + 26 张 M* 主数据表）
  • DynamoDB 承载高弹性、schema-less 的 5 张表，采用 分区键 + 排序键 设计 （如 travel 表以 travel_no 为分区键、data_type 为排序键、json_data 存半结构化 JSON）， 实现单表多实体，避免表数量膨胀
  • S3 承载文件实体（ap-northeast-1 区域）
  • Sequence 表用 seq_key/seq_no 提供分布式序列号
  • 可量化效果：scan-limit=10000 控制扫描边界；表名带环境前缀，实现「1 账户 1 集群」隔离。 🔶 建议补充：单表承载的实体种类数、查询延迟数据。
  • 可套用主题：数据架构、大数据、微服务（每个主题都会问"数据怎么存"）

⑥ Serverless 数据同步链路（最终一致性）

  • 问题：DynamoDB（服务端写入）与 MySQL（报表/既有系统查询）之间需要同步， 但同步逻辑若放在 Java 服务里，会拉长主链路响应时间，且扩容成本高。
  • 方案：事件驱动的 Serverless 同步： DynamoDB Stream 与 SQS 作为事件源触发 14 个 Lambda 函数， 按业务域拆分（import_travel_information、import_document_information、 import_message_thread、import_booking_information、import_mail_information、 import_parental_consent、import_notification、import_wallet_status 等）， 每个函数独立 Dockerfile、独立 GitHub Actions 工作流、独立 SAM 部署， 配置从 SSM Parameter Store 读取，用 aws_lambda_powertools 做日志/链路追踪/批量部分失败处理。 主链路只写 DynamoDB 即返回，同步异步化，达成最终一致性。
  • 可量化效果：14 个函数按域独立扩缩容；单个函数故障不影响其他业务域。 🔶 建议补充：同步延迟（秒级）、峰值消息处理量、按需计费节省的成本比例。
  • 可套用主题：云原生、FaaS、数据架构、高可用（近两年最热，强烈建议准备）

⑦ 批量消息推送的幂等与重试

  • 问题：客户消息（顧客メッセージ）常需批量推送（BulkPutCustomerMessage）， 邮件发送（MailSendJob、AutomaticEmailCreateJob）存在网络抖动、 第三方邮件网关限流，重试若不加控制会产生重复发送， 对客户是严重体验事故。
  • 方案：
  • 幂等控制：app.batch.idempotency-duration-minutes=10 时间窗去重
  • 专用重试服务：MailSendRetryService 独立承担重试，与业务解耦
  • 事务边界：service/transaction/*TransactionalService 拆分事务粒度
  • 可观测：Prometheus PushGateway（shutdown-operation: post）上报作业指标
  • 可量化效果：重复发送被幂等窗口拦截；作业失败可观测、可重跑。 🔶 建议补充：重试成功率、重复发送率降到多少。
  • 可套用主题：批处理、高可用、数据一致性

⑧ 跨国多时区时间一致性

  • 问题：系统服务日本本部（源库为 JST）、部署环境与开发终端时区各异 （容器为 UTC、开发机为 UTC+8）。 预约时间、截止时间、邮件发送时刻等一旦跨时区比较出错， 会出现「提前发送」或「漏发」——对旅游业务是不可接受的。
  • 方案：确立时间口径单一化原则： 存储统一 UTC，展示按业务方时区（JST）转换，转换动作集中到 FormatUtils 等工具类， 禁止在业务代码中散落 LocalDateTime.now()； 批处理的 executionBaseDate、acquisitionRange 作为 JobParameter 显式传入，不依赖系统时钟。
  • 可量化效果：时间比较错误集中收口；批处理基准日期可重放（同一参数结果可复现）。 🔶 建议补充：改造前时区相关缺陷单数量。
  • 可套用主题：数据架构、批处理、国际化系统架构（特色素材，别人写不出来，容易出彩）

⑨ 分布式会话与在线扩容

  • 问题：Web 层多实例部署后，Session 若存本地内存，用户会被反复踢下线。
  • 方案：引入 Spring Session Data Redis，接 Redis Cluster（6 节点）， 客户端 Jedis；spring.session.timeout=3600。 安全侧配合 spring-session 与 Spring Security 的会话并发控制。
  • 可量化效果：Web 实例无状态化，可水平扩容；实例重启不掉线。 🔶 建议补充：扩容后支撑的并发用户数、会话序列化后的请求延迟。
  • 可套用主题：高可用、高性能、微服务

⑩ 主数据统一（MDM）与外部系统联动

  • 问题：H.I.S. 集团存在 MDM（Master Data Management）主数据平台， 本国、城市、航空公司、货币等主数据需与 BASE HOME 保持一致， 人工维护必然不一致。
  • 方案：ImportMdmJob 定时从 MDM API 拉取主数据落库， 经 api/mdm/ 封装认证与查询参数； 本地保留 26 张 M* 主数据表作为只读副本，业务查询不直连外部。
  • 可量化效果：主数据一致性由作业保障，业务侧零改造。 🔶 建议补充：主数据同步频率、覆盖的主数据表数量。
  • 可套用主题：系统集成、数据架构、企业应用集成（EAI）

第 2 段 · 架构设计（约 800 字，本文核心）

必须先讲「拆分依据」——这是区分架构师与工程师的关键。

推荐三个拆分维度（本项目真实成立）：

维度一：按伸缩特征拆分

Web 层承载营业本部员工的交互操作，流量呈工作日昼间高峰特征； Batch 层承载成本文件生成、邮件发送等定时作业，呈夜间定时峰值且瞬时资源占用大； FaaS 层承载数据同步，呈持续低频特征。 若合并部署，批处理的资源峰值会直接冲击在线预约接口的响应时间。 因此我将三者拆分为独立部署单元，使各层可按自身曲线独立扩缩容。 权衡说明：这牺牲了单体部署的调用简单性，换来了资源隔离与独立伸缩能力。

维度二：按访问协议与调用方拆分

内部服务间采用 gRPC（base-home-service 暴露 6565 端口，17 个 RPC）， 而非 REST。原因是服务间调用对性能与强类型契约更敏感，gRPC 基于 HTTP/2 多路复用 且由 proto 保证强类型；对外则通过 Web 层的 REST 接口（/api/v1/**）暴露， 兼顾浏览器友好性与前后端契约稳定性。

维度三：按数据存储特征拆分（本项目最有说服力的一点）

我采用混合存储（Polyglot Persistence）： Aurora MySQL 承载强一致交易与复杂关联查询（79 张业务/主数据表）； DynamoDB 承载 5 张 schema-less 高弹性表（travel / document / parental / sequence / message_thread）；S3 承载文件实体。 服务边界与数据边界对齐，避免多个服务共享同一张表造成的隐性耦合。

第 3 段 · 关键技术实现（约 700 字）

要素一：契约驱动的服务通信

系统需同时为 Java、Go、PHP 三种技术栈的调用方提供服务。 我在 base-home-spec 模块中以 protobuf 作为唯一契约源， 通过构建脚本编排 build-java → build-go → build-php → generate-all， 分别生成三语言产物并独立发布（Maven / Go module / Composer）。 同时用 --openapiv2_out 产出 OpenAPI 描述文件，经 MkDocs 发布为在线文档。 该设计使「17 个 RPC 的接口口径」在三端天然一致， 把接口不一致问题从「运行时联调发现」提前到「构建期暴露」。

要素二：服务端的分发与复用

base-home-service 采用单一入口 BaseHomeService（@GRpcService）承接 17 个 RPC， 统一经 execute(IGrpcService, req, respObserver) 方法分发到各业务实现类， 共 18 个实现类；跨业务域的能力（文档、消息线程、亲权同意书、 序列号、旅行信息）下沉到 service/shared/ 复用， 避免同一逻辑在多个 RPC 中重复实现。

要素三：构建期依赖治理

项目通过独立的 base-home-versions Gradle 插件统一版本源 （base-home.versions.gradle），各模块以 apply plugin: 'base-home.versions' 接入， 并用 resolutionStrategy { force ... } 锁定关键组件。

示例（难点 ②）：

我们在升级 protobuf 依赖时，proto-google-common-protos 被解析到 2.64.0-rc1， 导致 gRPC 服务启动直接失败。更棘手的是，由于版本声明采用了动态区间 （protobufVersion = '[3,4)'、grpcVersion = 'latest.release'）， 该问题在构建期完全不显现，只在运行时暴露——这属于典型的依赖漂移风险。 我的判断是：这不是一次偶发故障，而是「版本契约不明确」这一架构缺陷的必然结果。 因此我没有只做局部修复，而是在统一版本源中将该组件强制锁定到 2.63.2， 并同步锁定 MyBatis 3.0.5 等关键组件，把隐式版本变成显式契约。 改造后构建具备可复现性，同一提交在任何机器上产物一致。

第 2 段 · 架构设计（约 800 字）

分三层论述：

第一层：容器化与交付

Web（8080）、Service（gRPC 6565）、Batch（无 Web 容器， spring.main.web-application-type: none）各自独立 Dockerfile 与镜像， 镜像基于集团统一基础镜像，保证运行时基线一致。 本地研发环境通过 TestContainers 拉起 MySQL， 通过 LocalStack（:4566）模拟 DynamoDB 与 S3， 使「本地能跑通」与「云上能跑通」的技术栈一致，消除了环境差异导致的缺陷。

第二层：Serverless 数据同步（本文核心）

系统的写入主链路落在 DynamoDB，而报表与既有系统仍需从 MySQL 查询。 若在 Java 服务中同步写两侧，主链路响应时间会被拉长， 且同步逻辑的扩容需求会绑架整个服务的资源配置。 因此我把同步链路设计为事件驱动的 Serverless 架构：

  • 事件源：DynamoDB Stream（写后事件）+ SQS（业务消息队列）
  • 计算单元：14 个 Lambda 函数，按业务域拆分
  • 配置源：SSM Parameter Store
  • 可观测：aws_lambda_powertools 提供结构化日志、Tracer 链路追踪 与 SQS/Stream 批量处理工具

按触发方式可分为两类： | 触发方式 | 函数 | |---|---| | DynamoDB Stream | import_document_information、import_message_thread、import_parental_consent、import_travel_information、send_travel_information | | SQS | import_booking_information、import_mail_information、import_notification、import_wallet_notification、import_wallet_status、update_travel_status | | 定时 | send_email_footer、send_email_template、send_todo_information |

权衡说明：该设计以最终一致性替代强一致性——主链路返回时， MySQL 侧数据尚未更新。评估后我们认为对报表与通知场景可接受， 而预约写入等强一致场景仍走关系库事务，不做异步化。

第三层：函数粒度划分原则

我没有按「一张表一个函数」划分，而是按业务域划分。 理由：同一业务域的实体更新往往需要一起处理（如旅行信息变更需同步 申请人与预约数据），按表拆会导致函数间编排复杂、 且同一业务逻辑被多次触发。按域拆分使每个函数内部可完成完整的业务处理， 同时故障域按业务隔离——某个域的函数异常不会波及其他业务。

第 3 段 · 关键技术实现（约 700 字）

要素一：事件驱动的解耦

主链路只写 DynamoDB 即返回，同步由 Stream 异步接管， 把「写数据库」与「同步数据」两个关注点彻底解耦。 🔶 补充：主链路响应时间从 X ms 降到 Y ms。

要素二：批量处理与部分失败

Lambda 处理 SQS/Stream 批次时，单条记录失败不应导致整批重试。 我们使用 aws_lambda_powertools 的 batch 处理工具， 支持部分批次失败语义，仅将失败记录投入死信队列，正常记录正常提交。

要素三：配置与密钥管理

所有配置（数据库连接、SNS Topic ARN、外部端点）统一从 SSM Parameter Store 读取（aws/ssm_client.SsmClient）， 代码仓库中不落任何明文凭证。 服务端侧同样采用 STS AssumeRole 获取临时凭证 + DefaultCredentialsProvider 兜底， 避免长期凭证泄露风险。

要素四：独立交付流水线

每个 Lambda 拥有独立的 Dockerfile 与独立的 GitHub Actions 工作流 （按 import-* / send-* / update-travel-status 命名）， 支持单函数灰度与回滚，部署动作通过 SAM 完成。 这带来一个重要收益：单个函数的变更不需要整体回归。

难点示例（⑥）：

挑战在于同步延迟与顺序性。DynamoDB Stream 保证同一分区的记录有序， 但跨分区不保证。若两个业务域的数据存在先后依赖， 并行处理可能产生顺序错乱。我们的应对是： 把存在依赖关系的实体收敛到同一分区键下（如旅行信息统一以 travel_no 为分区键）， 借由 Stream 的分区内有序性保证处理顺序； 对确实跨域的场景，采用幂等 + 版本号的设计， 使乱序到达的更新可以通过比较版本号判定是否过期，避免旧数据覆盖新数据。

旅游业务的数据形态差异极大，我将其归纳为四类： ① 强一致交易数据——预约、申请人、旅行者、费用，要求事务与关联查询； ② 频繁演进的半结构化数据——旅行主信息字段随业务政策频繁增删， 若用关系表承载则每次变更都需 DDL； ③ 文件实体——护照、文档、亲权同意书，体积大且需对象存储能力； ④ 高频读写的小数据——消息线程、序列号，读写频繁且要求低延迟。 用单一存储承载这四类数据，必然在某一方面做出妥协。

第 2 段 · 架构设计（约 800 字，本文核心）

第一层：混合存储选型（Polyglot Persistence）

数据类型 存储选型 选型依据
强一致交易 Aurora MySQL 需要事务、外键、复杂关联查询；79 张表（26 张 M* 主数据 + 53 张 T* 业务）
半结构化/弹性 DynamoDB 5 张表 schema-less、按需扩缩、毫秒级延迟，字段演进无需 DDL
文件实体 S3（ap-northeast-1） 对象存储，与数据库解耦，降低库体积与备份成本
分布式序列号 DynamoDB sequence 表 需跨实例唯一且自增，关系库自增无法满足分布式场景

第二层：DynamoDB 单表多实体设计（本项目的技术亮点）

我采用分区键 + 排序键 + JSON 载荷的模式实现单表多实体： 以 travel 表为例，分区键为 travel_no（旅行编号）， 排序键为 data_type（数据类型），实体内容存于 json_data 字段。 这样一张表可承载同一旅行下的多种数据类型， 既避免了表数量随业务类型线性膨胀， 又保证同一旅行的所有数据落在同一分区，查询时可用一次 Query 取回， 无需跨分区扫描。

其余四张表： - document —— 文档元数据（文件实体在 S3） - parental —— 亲权同意书（親権同意書） - message_thread —— 消息线程 - sequence —— 序列号（seq_key / seq_no），为分布式环境提供唯一编号

治理措施：表名统一带环境前缀，实现「1 账户 1 集群」的环境隔离； scan-limit 设为 10000，为全表扫描设置硬边界，防止误用 Scan 拖垮表。

第三层：批处理读写分离

批处理既要大量读取（成本文件生成、外部预约导入、ToDo 状态更新）， 又要回写结果。我为其配置双数据源： ReaderDataSourceConfig（spring.datasource.reader）与 WriterDataSourceConfig（spring.datasource.writer，标 @Primary）， 通过包路径隔离 Mapper（repository/reader/ 与 repository/writer/）， 使读写请求物理分离，批量作业不再争抢在线业务的连接池资源。 同时设置事务隔离级别为 TRANSACTION_READ_COMMITTED， 避免长事务期间大量持有间隙锁影响在线写入； defaultFetchSize = 200 控制批量游标，防止一次性载入海量结果集导致 OOM。

第 3 段 · 关键实现（约 700 字）

要素一：数据访问层设计

MySQL 侧统一使用 MyBatis（3.0.5，在统一版本源中强制锁定， 覆盖 Spring Boot 托管版本以保证行为一致）， 79 个实体按职责分两个 source set 组织，主数据实体与业务实体分离； 54 个 Mapper 按业务域归入 repository/。 DynamoDB 侧通过 DynamoDbEnhancedClient 提供对象映射， 由 DynamoDbRepository 基类封装通用操作， 实体以 @DynamoDbBean 注解声明， 属性名集中定义在 consts 包（TravelConsts、DocumentConsts 等）， 避免魔法字符串散落。

要素二：一致性与重试

DynamoDB 侧启用乐观锁重试（@EnableRetry， 重试 4 次、间隔 500ms），应对并发写入冲突。 跨存储一致性通过事件驱动链路达成最终一致（DynamoDB Stream → Lambda → MySQL）。

要素三：CSV 与文件下载

成本文件（ACT 原价 / AIR 机票 / HTL 酒店）使用 SuperCSV 注解库 将实体直接映射为 CSV，配合 CsvDownloader 接口与 FileUploadService 落 S3，避免大文件在内存中拼装。 导出列定义通过注解集中在实体上，新增列不会波及导出逻辑。

要素四：主数据治理

集团 MDM 主数据由 ImportMdmJob 定时同步，本地保留 26 张 M* 表作为只读副本， 业务查询不直连外部系统——既保证主数据一致性，又隔离了外部系统故障对业务的影响。

第 2 段 · 架构设计（约 800 字）

第一层：资源隔离——消除单点相互影响

可用性最大的敌人往往不是外部攻击，而是内部资源争抢。 本项目最典型的场景是：批处理需要从生产库大量读取并回写结果， 而在线预约接口同时也在访问同一数据库。 若共享连接池，夜间批处理峰值会直接拖慢甚至拖垮在线接口。

我的方案是为批处理配置双数据源： ReaderDataSourceConfig（spring.datasource.reader）与 WriterDataSourceConfig（spring.datasource.writer，@Primary）， 通过包路径隔离 Mapper（repository/reader/ 与 repository/writer/）。 读写物理分离后，批量作业不再与在线业务争抢同一数据源连接。

同时设置 TRANSACTION_READ_COMMITTED 隔离级别， 减少长事务持有锁的时间；defaultFetchSize = 200 控制游标， 防止海量结果集一次性载入导致内存溢出——这是批处理最常见的 OOM 诱因。

第二层：故障隔离——按部署单元切分故障域

Web、Service、Batch、FaaS 各自独立部署： - Batch 模块设置为 web-application-type: none，不占用 Web 端口， 与 Web 层无任何进程级耦合 - FaaS 侧 14 个 Lambda 按业务域拆分，单个函数故障不会波及其他业务域 - 每个函数独立镜像、独立流水线、独立部署，支持单函数灰度与快速回滚

权衡说明：这增加了运维单元数量与管理复杂度， 但把「一个模块崩溃导致全站不可用」的风险降为「单个业务域受影响」。

第三层：状态外置——支撑水平扩容

Web 层多实例部署后，若 Session 存于本地内存， 负载均衡会把用户请求分发到不同实例，导致反复掉线。 我引入 Spring Session Data Redis，接入 Redis Cluster（6 节点）， 客户端使用 Jedis，会话超时设为 3600 秒。 会话外置后，Web 实例完全无状态，可任意水平扩容与重启而不影响在线用户。

第四层：数据层可靠性

DynamoDB 侧启用乐观锁重试（@EnableRetry，重试 4 次、间隔 500ms）， 应对并发写入冲突；文件实体落 S3 而非数据库， 降低库体积与备份恢复时长；主数据保留本地只读副本（26 张 M* 表）， 使外部 MDM 系统故障不影响业务查询。

第 3 段 · 关键技术实现（约 700 字）

要素一：幂等控制——防止重复推送

客户消息与邮件推送是本系统的可靠性敏感点：一旦重复发送， 对客户是直接的体验事故。我们设计了多层防护： - 幂等时间窗：app.batch.idempotency-duration-minutes = 10， 同一业务键在窗口内重复触发会被拦截 - 专用重试服务：MailSendRetryService 独立承担重试逻辑， 与业务处理解耦，避免重试代码侵入业务流程 - 事务粒度拆分：service/transaction/*TransactionalService 将事务边界 控制在必要范围内，避免大事务回滚造成的连带重放 - 投递状态跟踪：TEmailDeliveryManagement 表记录投递状态 与 update_travel_status 函数联动，形成可追溯的闭环

要素二：可观测性——故障可发现才可恢复

高可用的前提是「故障能被及时发现」。 Batch 侧通过 Prometheus PushGateway 上报作业指标 （配置 shutdown-operation: post，确保作业结束前完成指标推送）， 使批处理这类短生命周期进程的运行状态可被监控系统采集。 FaaS 侧使用 aws_lambda_powertools 的 Logger 与 Tracer 输出结构化日志与链路追踪信息。

要素三：作业可重跑与可复现

批处理的重跑能力是可靠性的重要保障。 我们将 executionBaseDate、acquisitionRange、importTargetType 等关键参数定义为 JobParameter 显式传入，不依赖系统时钟， 使同一参数的重跑结果完全可复现。 🔶 补充：这解决了什么具体的补数场景。

第 2 段 · 架构设计（约 800 字）

按安全架构的经典四层组织：身份认证 → 访问控制 → 数据安全 → 安全审计

第一层：身份认证（Authentication）

系统采用 OAuth2/OIDC 协议实现统一身份认证， Web 层通过 spring-boot-starter-oauth2-client 接入集团统一认证服务， 以授权码模式完成登录，令牌校验使用 spring-security-oauth2-jose（JOSE/JWT）。 用户身份属性通过 user-name-attribute 配置从令牌中提取， 避免依赖本地用户表——这使账号生命周期由集团统一治理。

同时通过 thymeleaf-extras-springsecurity6 把安全上下文暴露到视图层， 使页面元素的显隐可以直接由权限决定，而不是靠前端 JavaScript 隐藏 （后者只是「看不见」，后者才能做到「点不到」）。

权衡说明：OIDC 引入了对外部认证服务的依赖， 我们通过将用户信息缓存于会话中，使认证服务短暂不可用时 已登录用户仍可继续操作，避免认证服务成为可用性单点。

第二层：访问控制（Authorization）

授权模型我采用 RBAC + 接口级 scope 校验的组合。 角色维度划分为管理员（admin）、操作员（operator）、 主管（chief）、VIP 等，各角色持有不同的权限 scope 列表。 权限校验下沉到接口层（/api/v1/** 由 Spring Security 统一拦截）， 而非散落在各 Controller 的业务代码中—— 这样新增接口时权限是「默认拒绝」而非「默认放行」， 从架构上避免了「忘记加权限注解」这类遗漏风险。

第三层：数据安全（Data Security）

传输安全：内部服务间 gRPC 调用使用 TLS （endpoint 采用 tls:// 前缀），对外 Web 访问全站 HTTPS。 凭证安全：这是我重点处理的部分。 系统不使用长期固定的 AWS 密钥，而是通过 STS AssumeRole 获取临时凭证，配合 DefaultCredentialsProvider 兜底， 凭证自动轮换，即使泄露其有效期也极短。 配置安全：FaaS 侧所有配置（数据库连接、外部端点） 统一从 SSM Parameter Store 读取，代码仓库中不落任何明文凭证。 存储安全：文件实体统一存放 S3，数据库仅保存文件引用； 数据库账号按 reader/writer 职责分离，批处理读账号无写权限。

第四层：安全审计（Audit）

系统在 Web 层设置独立的审计能力： 画面操作日志由 system 域的控制器统一记录， 关键业务操作（预约变更、消息发送、主数据修改） 均留存操作者、操作时间与操作内容。 审计日志与业务数据分离存储，避免业务回滚时日志同时丢失。

第 3 段 · 关键技术实现（约 700 字）

要素一：会话安全

会话由 Spring Session Data Redis 统一管理， 存储于 Redis Cluster（6 节点），超时时间 3600 秒。 相比本地会话，集中式会话带来两个安全收益： 一是会话数据不落在应用服务器磁盘上，降低主机被入侵后的会话窃取风险； 二是可在服务端强制失效任意会话，实现「管理员踢出用户」 与「用户改密后全端下线」这类安全能力。

要素二：凭证与密钥的集中治理

我把凭证获取统一收口到配置类（DynamoDbConfig、 AwsConfig、SsmClient），业务代码不直接接触凭证。 这样做的价值在于：凭证轮换、加密算法升级、 权限范围调整都只需在单一位置修改，不会遗漏调用点。 环境隔离同样重要——DynamoDB 表名统一带环境前缀， 实现「1 账户 1 集群」，防止测试环境误连生产数据。

要素三：接口契约中的安全边界

由于系统通过 protobuf 向 Java/Go/PHP 三端提供接口， 契约本身也承担安全职责： 每个 RPC 均声明 HTTP 映射（google.api.http）， 统一走 /v1/<RpcName> 路径，便于在网关层集中做鉴权与限流； 错误信息通过统一的 Error{code,message} 结构返回， 对外只暴露错误码与友好提示，不泄漏堆栈与内部实现细节。

要素四：输入校验与注入防护

Web 层启用 spring-boot-starter-validation 做参数校验， 数据库访问全部通过 MyBatis 参数绑定，杜绝字符串拼接 SQL。 涉及 HTML 内容处理的场景使用 Jsoup 做净化， 防止存储型 XSS——这在客户消息场景尤其重要， 因为消息内容会在 MyPage 页面回显给其他用户。

第一层：契约单一来源（Single Source of Truth）

我把 base-home-spec 模块确立为唯一的接口契约源， 所有接口以 protobuf 定义，统一存放于 his/base/home/v1/ 目录， 按职责分层组织： - basehome_service.proto —— 服务定义（BaseHomeService，17 个 RPC） - request/ —— 17 个请求消息 - response/ —— 17 个响应消息 - enums/ —— 13 个枚举（产品类型、文档类型、申请人类型、消息状态、 销售渠道、发送者类型、保险类型等） - type/ —— 约 42 个可复用消息（含统一的 Error{code,message}）

全部约 90 个 proto 文件纳入版本管理，任何接口变更都必须 通过该模块提交，从流程上杜绝了「各写一份」的可能。

层次化组织的价值：type/ 中的可复用消息（如地址、金额、 旅行者基础信息）被多个 request/response 引用， 避免了同一结构在 17 个接口中重复定义 17 次—— 这是契约可维护性的关键。

第二层：构建期多语言产物生成

契约定义统一后，我在构建脚本中编排了完整的生成链路： build.sh 按 build-java → build-go → build-php → generate-all 顺序执行， 每种语言使用各自的官方插件：

目标语言 生成方式 产物形态
Java protobuf-gradle-plugin（protoc + protoc-gen-grpc-java） 发布至内部 Maven
Go 容器内 protoc（--go_out / --go-grpc_out / --grpc-gateway_out） Go module zip
PHP --php_out + grpc_php_plugin Composer 包
文档 --openapiv2_out → MkDocs 在线 API 文档

关键设计：把「生成」纳入构建流水线而非依赖人工执行， 使接口一致性问题从「运行时联调发现」提前到「构建期暴露」—— 这是本次集成设计最重要的收益。

权衡说明：多语言生成的构建链路复杂度显著上升 （需维护 Docker 化的 protoc 环境、三套发布流程）， 但相比接口不一致导致的线上缺陷与联调返工，这个成本是值得的。

第三层：对外依赖本地化

集团 MDM 主数据平台是外部系统，若业务查询直连外部， 则外部系统的任何抖动都会直接传导到业务操作。 我采用本地只读副本策略：通过 ImportMdmJob 定时从 MDM API 拉取主数据， 落地为 26 张 M* 主数据表，业务侧只查本地。 这样 MDM 平台短暂不可用时业务不受影响， 数据新鲜度通过同步频率控制，是「可用性优先」的合理取舍。

第 3 段 · 关键技术实现（约 700 字）

要素一：通信协议选型

服务间通信选择 gRPC 而非 REST，依据有三： ① HTTP/2 多路复用，在高频内部调用下连接利用率更高； ② protobuf 二进制编码体积小、序列化开销低； ③ 强类型契约天然由 proto 保证，与我们的契约单一来源策略一致。 服务端监听 6565 端口，单次消息上限设为 64MB （旅游业务存在较大报文，如批量消息与文件列表）， 并开启 gRPC Reflection 便于调试期接口探查。

对外则通过 Web 层的 REST 接口（/api/v1/**）暴露， 兼顾浏览器友好性与前端契约稳定性， 并用 SpringDoc 生成 OpenAPI 描述（/api-docs）。

要素二：服务端的分发设计

base-home-service 以单一入口类 BaseHomeService （@GRpcService，继承 proto 生成的 BaseHomeServiceImplBase）承接 17 个 RPC， 统一经 execute(IGrpcService, req, respObserver) 方法分发。 业务逻辑委托给 18 个实现类（均实现 IGrpcService 接口）。 这一设计的价值在于：横切关注点集中—— 日志、异常转换、认证上下文校验都可在 execute 中统一处理， 各业务实现类只关注业务逻辑，避免每个 RPC 重复编写样板代码。

权衡说明：单一入口在 RPC 数量极大时会成为维护瓶颈， 但 17 个 RPC 的规模下，统一分发带来的横切收益大于其复杂度成本。

要素三：跨业务域能力复用

多个 RPC 需要的能力（文档、消息线程、亲权同意书、 序列号、旅行信息）下沉到 service/shared/ 中的 5 个服务， 避免同一逻辑在多个 RPC 中重复实现。 文件相关能力单独归入 service/filesystem/。

要素四：错误契约统一

proto 中定义统一的 Error{code, message} 消息， 所有接口的错误返回结构一致，调用方可编写统一的错误处理逻辑， 无需为每个接口单独适配。错误码体系与 his-common 的消息 ID 规范对齐 （如 EABH00001 形式的错误码），使错误在服务端、Web 端与 文档中具有一致的标识。

问题：契约统一后，新的问题出现了—— 契约的「消费者」不止我们的服务，还包括 protobuf 官方的公共类型库。 一次依赖升级中，proto-google-common-protos 被解析到 2.64.0-rc1， gRPC 服务启动直接失败。更棘手的是，由于我们的版本声明采用了 动态区间（protobufVersion = '[3,4)'、grpcVersion = 'latest.release'）， 这个问题在构建期完全不显现，只在运行时暴露。

第 2 段 · 评估方法与过程（约 800 字，本文核心）

推荐用 ATAM 四阶段组织：

阶段一：场景和需求收集

我组织了由业务方（营业本部代表）、运维方、开发负责人参与的评估会议， 采用 效用树（Utility Tree） 对质量属性需求进行优先级排序。 排序依据为「重要性」与「实现难度」两个维度， 高重要性且高难度的需求优先投入架构资源。 经排序后，性能与可用性被列为最高优先级， 可修改性次之（因业务政策变动频繁，接口与字段需持续演进）。

阶段二：架构视图和场景实现

我以视图为单位描述架构对场景的支撑，本项目主要涉及四个视图： - 逻辑视图：8 个 Gradle 模块的职责划分与依赖方向 - 开发视图：common（实体/常量/消息）、spec（契约）、 versions（版本治理）等支撑模块的组织 - 进程视图：Web（8080）、Service（gRPC 6565）、Batch（无 Web 容器）、 FaaS（14 个 Lambda）的运行时交互 - 部署视图：AWS ap-northeast-1，多实例部署 + Redis Cluster + Aurora + DynamoDB + S3 + SQS/SNS

阶段三：属性模型构造和分析

针对性能与可用性，我们构造了简化的分析模型： - 性能：分析关键路径（Web → gRPC → DynamoDB）， 识别出 DynamoDB 查询是否落在单一分区是主导因素， 因此把分区键设计作为性能敏感点重点评审 - 可用性：分析方法是将部署单元逐个标记为「失效」， 观察影响范围。分析中发现 Batch 与 Web 共享数据源时， 批处理峰值会传导为在线接口延迟——这成为后续读写分离的直接依据

阶段四：架构决策与折中

评估的核心产出是识别权衡点并形成决策记录。本项目的三个主要权衡：

权衡一：混合存储（MySQL + DynamoDB + S3） - 正向：性能↑（DynamoDB 低延迟、单分区查询）、可修改性↑（schema-less，字段演进免 DDL） - 负向：可维护性↓（多套存储的备份/容量规划）、一致性↓（需事件驱动达成最终一致） - 决策：接受。理由是四类数据的访问特征差异足够大，统一存储的代价更高。

权衡二：Serverless 数据同步 - 正向：性能↑（主链路解耦）、成本↓（按需计费）、可用性↑（故障域隔离） - 负向：一致性↓（最终一致）、可测试性↓（本地调试困难） - 决策：接受。理由是同步场景对延迟不敏感，且用 moto/LocalStack 缓解了测试困难。

权衡三：契约单一来源 - 正向：可修改性↑（接口变更一处生效）、可测试性↑（构建期暴露不一致） - 负向：构建复杂度↑（需维护 Docker 化 protoc 环境与三套发布流程） - 决策：接受。理由见难点素材 ①。

第 2 段 · 架构设计（约 800 字，本文核心）

第一层：资源隔离——读写分离双数据源

批处理最大的架构风险不是作业本身失败，而是批量作业拖垮在线业务。 成本文件生成需要扫描大量费用明细，外部预约导入需要回写大量记录， 若与在线接口共享数据库连接池，夜间批次高峰会直接推高在线接口延迟。

我的方案是配置双数据源： - ReaderDataSourceConfig（spring.datasource.reader）—— 只读账号，承担大量查询 - WriterDataSourceConfig（spring.datasource.writer，标 @Primary）—— 写账号，承担结果回写

通过包路径隔离 Mapper（repository/reader/ 与 repository/writer/）， 使读写走不同数据源，物理层面互不干扰。 配合的优化还包括： - 事务隔离级别设为 TRANSACTION_READ_COMMITTED， 避免长事务期间持有大量间隙锁影响在线写入 - mybatis.defaultFetchSize = 200 控制批量游标， 防止一次性载入海量结果集导致 JVM 内存溢出—— 这是批处理最典型的故障模式

权衡说明：双数据源增加了配置复杂度， 且跨数据源无法使用单一事务（需业务上避免跨源事务）， 但换来的在线业务稳定性收益远大于此成本。

第二层：作业组织与复用

10 个作业统一继承 job/base/ManagedBaseJob 基类， 把作业的公共能力（参数解析、日志、异常处理）收敛到基类， 各作业只关注自身业务逻辑。 业务逻辑下沉到 service/ 层的对应服务 （MailSendService、ImportMdmService、FileCreateService 等）， 使作业类只承担编排职责，业务逻辑可被测试与复用。 作业参数通过枚举统一定义（JobParameterKey）： acquisitionRange（取得范围）、executionBaseDate（执行基准日）、 todoDistinction、emailType、importTargetType。

第三层：作业的可靠性设计

  • 幂等控制：app.batch.idempotency-duration-minutes = 10 提供时间窗去重，防止重复执行造成重复推送
  • 专用重试服务：MailSendRetryService 独立承担邮件重试， 与业务解耦，重试策略可独立调整
  • 事务粒度控制：service/transaction/*TransactionalService 把事务边界限制在必要范围，避免大事务回滚造成连带重放
  • 可观测性：通过 Prometheus PushGateway 上报作业指标 （shutdown-operation: post 确保短生命周期进程在退出前完成指标推送）， 使定时作业的运行状态可被监控系统采集与告警

第四层：元数据驱动的通用查询

GenericQueryExecutionJob 配合 MGenericQuery* 系列表， 把查询逻辑外置为元数据配置，新增一类查询只需配置数据而无需改代码。 这一设计显著提升了批处理的可修改性—— 业务侧新增报表类查询不再需要开发排期。

第 3 段 · 关键技术实现（约 700 字）

要素一：CSV 文件生成与上传

三类成本文件（ACT/AIR/HTL）使用 SuperCSV 注解库实现， 通过注解将实体字段直接映射为 CSV 列， 导出列定义集中在实体上（ActivityCostDownloadCsv、 AirCostDownloadCsv、HotelCostDownloadCsv）， 配合 CsvDownloader 接口与 FileUploadService 落 S3。 设计价值：新增导出列时只需修改实体注解， 不会波及导出逻辑代码——这是「限制变更影响范围」的可修改性战术。

要素二：外部数据导入

外部预约数据导入（ExternalReservationImportJob） 通过 RecvImportType 枚举区分导入类型， 经 ExternalReservationImportService 处理入库。 集团主数据联动（ImportMdmJob）通过 api/mdm/ 封装的 认证与查询参数访问 MDM API，本地落为 26 张 M* 主数据表。

要素三：消息通知联动

批处理完成后需推送通知，通过 SnsService 发布到 SNS 主题 （app.services.aws.sns），由下游 Lambda 消费。 这种「批处理产出 → SNS → Lambda 消费」的模式， 把批处理与通知渠道解耦：新增通知渠道无需修改批处理代码。

要素四：作业参数的显式化

我把 executionBaseDate（执行基准日）、acquisitionRange（取得范围） 等关键参数定义在 JobParameterKey 枚举中并显式传入， 而非在代码中直接取系统当前时间。 这一设计带来两个收益： ① 可重跑——补数时指定历史日期即可重新生成，结果与当日运行一致； ② 可测试——测试可固定参数，使结果可预期。 这对跨国系统尤其重要：服务日本本部（源库 JST）而容器运行于 UTC， 若依赖系统时钟取「今天」，跨时区下极易取到错误的日期边界。

难点示例（⑧ 多时区，批处理视角）：

问题：系统服务日本本部，源数据库运行于 JST， 而批处理容器环境为 UTC。这个差异在「取当天数据生成成本文件」 这类作业上会直接造成错误——容器认为的「今天」 在 JST 下可能还是「昨天」，反之亦然。 后果是成本文件漏当天的数据或重复包含前一天的数据， 而这类错误不会抛出异常，只会静默地产生错误结果。

方案：我的处理分两处。 第一处是存储口径统一：数据库中的时间统一以 UTC 存储， 展示与业务判断时按 JST 转换，转换动作集中到 FormatUtils 工具类， 禁止业务代码中散落直接取当前时间的调用。 第二处是批处理参数化：把 executionBaseDate 作为 JobParameter 显式传入而不依赖系统时钟，使作业的日期边界由调用方决定。 这带来的额外收益是可重放性——指定同一基准日重跑， 结果与当日运行完全一致，补数场景可靠。

效果：🔶 时区相关缺陷数量下降情况；作业结果可复现。

三、正文五段框架

第 1 段 · 项目背景与演化驱动力（约 400 字）

演化类论文的核心是「驱动力」——为什么必须变？

BASE HOME 的架构演化并非为了技术而技术，而是由三类真实驱动因素推动：

驱动一：调用方技术栈扩张 系统最初仅服务 Java 侧的 Web 应用，随着集团平台化推进， 周边 Go 平台与既有 PHP 系统也需接入。 若为每种语言各写一份接口定义，字段口径必然漂移。 这迫使我们在接口层做出根本性改变。

驱动二：数据形态复杂化 旅游业务的文档、亲权同意书、消息线程等数据字段演进频繁， 关系型模型的 DDL 变更成本越来越高， 促使我们引入 NoSQL 与对象存储，形成混合存储架构。

驱动三：云平台能力演进 AWS SDK v2 提供了 v1 所没有的 DynamoDB 增强客户端（DynamoDbEnhancedClient）， 而既有代码大量基于 v1。全量重写风险过高，必须寻找演进路径。

这三类驱动力共同决定：架构必须演化，但不能推倒重来。

第 2 段 · 演化策略与过程（约 800 字，本文核心）

第一原则：渐进式演进，拒绝大爆炸式重写

面对 AWS SDK v1 到 v2 的迁移，我们评估了两条路径：

方案 优点 风险
一次性全量迁移到 v2 技术栈彻底统一 涉及大量既有代码，回归范围不可控；业务不能停
v1/v2 按能力边界共存（采纳） 风险可控，新能力不受阻 双版本长期共存，依赖体积与维护成本上升

我们采纳了共存方案，并确立清晰的能力边界划分规则： - 新增能力一律走 v2——DynamoDB 增强访问、STS AssumeRole 临时凭证 - 既有能力暂留 v1——已稳定运行的 S3/STS 调用不做无谓改动 - 客户端构建集中收口——在 DynamoDbConfig、AwsConfig 中统一构建， 业务代码不直接创建客户端

这条规则的价值在于：它把「迁移」从一个需要排期的项目， 变成了一个随新增功能自然发生的渐进过程。 每新增一个功能，技术债就减少一点，而不需要专门立项。

这是我在本项目最重要的架构判断：技术债的偿还方式， 不一定是集中偿还，也可以是"增量稀释"。

第二原则：契约先行，用单一来源约束多方

面对多语言调用方的接口漂移问题，我在 base-home-spec 模块中 确立 protobuf 为唯一契约源，通过构建流水线 （build.sh：build-java → build-go → build-php → generate-all） 生成 Java、Go、PHP 三语言产物及 OpenAPI 文档。

演化视角的价值：契约先行不仅解决了当下的接口一致性问题， 更重要的它是可演化性的基础—— 因为契约集中，接口的版本演进、废弃标记、兼容性检查 都只需要在一个地方进行。分散的接口定义无法演化，只能重写。

第三原则：依赖显式化，把隐式契约变成可控状态

项目初期各模块独立声明依赖版本，部分采用动态区间 （protobufVersion = '[3,4)'、grpcVersion = 'latest.release'）。 这带来一个隐蔽的风险：构建产物不可复现—— 同一份代码在不同时间、不同机器上可能解析到不同版本。

我引入了独立的 base-home-versions Gradle 插件作为统一版本源， 各模块通过 apply plugin: 'base-home.versions' 接入， 并使用 resolutionStrategy { force ... } 锁定关键组件。

这不是一次预防性的重构——风险已经真实发生： proto-google-common-protos 被解析到 2.64.0-rc1 后， gRPC 服务启动直接失败。这次故障印证了 「隐式版本契约」是架构层面的缺陷，而非偶发问题。

第 3 段 · 演化过程中的具体改造（约 700 字）

改造一：数据存储的演化

从单一关系库演进为混合存储： Aurora MySQL 承载强一致交易（79 张表）、 DynamoDB 承载高弹性半结构化数据（5 张表）、 S3 承载文件实体。

演化策略：新数据类型直接落在新存储，既有数据不做迁移。 例如文档与亲权同意书这类新增业务，直接以 document / parental 表落 DynamoDB， 而既有交易数据保持在 MySQL。 这样避免了大规模数据迁移的风险，同时让架构逐步具备弹性能力。

代价与应对：跨存储的一致性通过事件驱动链路达成最终一致—— DynamoDB Stream / SQS 触发的 14 个 Lambda 函数负责将数据同步回 MySQL。 这条链路本身就是「演化」的产物：它使新旧存储可以并存而不失一致。

改造二：在线与离线处理的分离

批量作业从与在线业务共享数据库，演进为双数据源读写分离 （spring.datasource.reader / writer，按包路径隔离 Mapper）。 这一改造的直接动因是：批处理峰值会推高在线接口延迟。 改造后读写的物理隔离使两者互不干扰。

改造三：服务能力的沉淀与复用

随着 RPC 数量增长（当前 17 个），跨业务域的重复逻辑被识别并下沉： 文档、消息线程、亲权同意书、序列号、旅行信息 5 类能力 沉淀到 service/shared/，文件能力归入 service/filesystem/。 服务端也从「每个 RPC 一个类」重构为 「单一入口 BaseHomeService + execute() 统一分发」—— 横切关注点（日志、异常转换、上下文校验）得以集中处理。

难点示例（③，三段式）：

问题：DynamoDB 增强客户端只在 AWS SDK v2 提供， 而既有代码大量基于 v1。全量迁移涉及面广、回归风险不可控， 且业务不能停机等待。

方案：我判断这里的核心矛盾不是「技术选型」， 而是「如何在不停机、不失控的前提下完成技术栈演进」。 因此我没有选择一次性重写，而是按能力边界划分： 新增能力走 v2，既有能力暂留 v1， 客户端构建统一收口在配置类中，业务代码不直接创建客户端。 这样做的深层价值是——收口点就是未来的迁移点。 当某天要彻底移除 v1 时，只需改动配置类， 而不需要遍历所有业务代码。

效果：🔶 新功能开发不再受 SDK 版本阻塞； 🔶 凭证获取统一收口后，凭证类故障下降。 更重要的是，技术债从「需要专门立项偿还」 变成了「随新增功能自然稀释」。

整个演化过程历时【🔶 时间】，期间系统保持连续可用，

① 演化必须由业务驱动力推动，而非技术偏好；
② 渐进式演进的成本看似更高，但风险可控，

③ 把隐式契约显式化，是让架构「可演化」的前提。
