## 三、使用方式

### 方式一：直接背诵（推荐）

1. 从本目录的 `PDF/` 中打印你选定的 3～4 篇
2. 先背**摘要**（约 330 字）——摘要决定阅卷老师的第一印象
3. 再背**正文的五个小标题**——这是文章的骨架，考场上先写骨架再填内容
4. 最后背每篇结尾的「可复用要点」——这是该题型的得分关键句

### 方式二：改造后背诵

每篇末尾的「写作提示」列出了：
- **待替换数字清单** —— 把示例值换成你的真实数据
- **可复用要点** —— 提示哪些句子是"通用高分句"，可跨题目迁移
- **本文字数** —— 核对是否在 2500～3000 字区间

### 方式三：考场应急组合

若考题的问法不在上述 9 篇之内，按下列方式组合：

| 考题关键词 | 主用范文 | 可插入的段落 |
|---|---|---|
| 性能 / 响应时间 | 04 高可用 | 03 的读写分离、02 的事件驱动解耦 |
| 可维护性 / 可扩展性 | 09 演化 | 01 的契约单一来源、06 的统一版本管理 |
| 可靠性 / 容错 | 04 高可用 | 08 的幂等与重跑、02 的部分失败处理 |
| 数据处理 / 存储选型 | 03 数据架构 | 08 的游标限制与扫描边界 |
| 分布式 / 跨系统协作 | 06 系统集成 | 01 的契约生成链路、02 的配置治理 |
| 技术选型 / 方案对比 | 07 架构评估 | 03 的选型依据、02 的容器与函数取舍 |

## 四、必须守住的写作红线

### 4.1 项目中并不存在，**不要编造**

- Kubernetes / Istio / 服务网格 / 服务注册中心（Eureka / Nacos / Consul）
- 熔断器、限流组件（Sentinel / Hystrix / Resilience4j）
- 分库分表、ShardingSphere、读写分离**中间件**
  （**注**：项目有读写数据源隔离，但那是代码层的数据源分离，不是数据库中间件，二者不可混为一谈）
- 多活 / 异地多活 / 双活数据中心
- Redis 作为业务缓存
  （**注**：项目中 ElastiCache Serverless（Valkey）**仅用于会话存储**，不承载业务缓存，范文已按此口径表述）
- 堡垒机、入侵检测、国密算法、等级保护认证

### 4.2 项目中真实存在，**可放心引用**

以下技术均已在本项目落地，若考题涉及相关领域可以直接写，不必担心被追问：

| 领域 | 真实技术 |
|---|---|
| 计算 | ECS Fargate、AWS Batch、Lambda、EventBridge Scheduler、Step Functions |
| 存储 | Aurora MySQL、DynamoDB（含 Stream）、S3 |
| 消息 | SQS（FIFO）、SNS |
| 安全 | AWS WAFv2、Cognito（OIDC）、STS 临时凭证、Systems Manager Parameter Store |
| 会话 | ElastiCache Serverless（Valkey） |
| 框架 | Java 21、Spring Boot 3.5.7、Spring Batch、MyBatis、gRPC / Protobuf、Spring Retry |
| 构建 | Gradle 8.14.3、统一版本管理插件 |
| 可观测 | Prometheus PushGateway、结构化日志、链路追踪 |
| 测试 | TestContainers、LocalStack、Pytest |
| 基础设施 | CloudFormation（基础设施即代码） |

> **WAF 的说明**：早期版本的本表曾把 WAF 列为"不可编造"，这是**错误的**——
> 项目确实通过 CloudFormation 定义了 AWS WAFv2。已更正。

> 阅卷老师中不乏一线架构师。编造自己没用过的技术，一旦被追问细节就会露馅；
> 而"主动写出方案的不足与未采用的方案"，反而是有架构判断力的表现。
> 这一点在 04、05 两篇的结尾段有示范。
