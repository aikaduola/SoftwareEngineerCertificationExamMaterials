论微服务架构的设计与应用

微服务架构是一种将单一应用程序划分为一组小型服务的架构风格，每个服务运行在独立的进程中，服务之间通过轻量级的通信机制相互协作。微服务架构具有独立部署、技术异构、按需扩展等特点，能够有效应对业务复杂度的增长和快速交付的要求，但同时也带来了服务拆分、分布式数据一致性、服务治理等方面的新挑战。

摘要

本文以我参与建设的 H.I.S. BASE HOME 旅游业务平台为例，论述了微服务架构在该项目中的设计与应用。该平台是日本 H.I.S. 集团面向营业本部与旅行者建设的业务支撑系统，覆盖预约管理、客户消息、通知发送与主数据联动等核心业务，于 2024 年 3 月启动建设，2025 年 1 月上线运行。我在项目中担任系统架构师，负责服务边界划分、服务间通信契约设计与构建治理体系建设。针对业务伸缩特征差异大、跨语言调用契约易漂移、新旧技术栈需长期并存三大挑战，我按伸缩特征、访问协议与数据边界三个维度将系统划分为 Web、Service、Batch、FaaS 四类独立部署单元；以 Protocol Buffers 作为唯一契约源，驱动 Java、Go、PHP 三语言客户端生成；并通过统一版本管理插件把隐式依赖转为显式契约。系统上线后运行稳定，关键接口响应时间明显改善，接口一致性缺陷大幅下降，获得业务方认可。

正文

一、项目背景

随着日本旅游市场竞争的加剧和客户需求的日益个性化，H.I.S. 集团原有以人工受理为主的业务模式面临着越来越大的压力。营业本部在受理预约时需要在多个系统之间反复切换，客户消息与通知的发送依赖人工触发，不仅效率低下，而且容易出错。为此，集团决定建设 BASE HOME 平台，统一承载预约管理、客户消息、通知发送、文件管理与主数据联动等核心业务。

该平台于 2024 年 3 月启动建设，2025 年 1 月正式上线运行，服务集团 300 余家营业门店、约 5000 名业务人员以及累计 800 万名注册旅行者，日均处理预约约 3 万笔、各类通知与消息约 12 万条。系统基于 Java 21 与 Spring Boot 3.5.7 构建，部署于 AWS 东京区域。

我在项目中担任系统架构师，主要负责三个方面的工作：一是服务边界的划分与整体架构设计；二是服务间通信契约的设计与治理；三是构建体系与版本治理机制的建立。

项目启动时，我们面临着三个突出的架构挑战。第一，平台承载的业务在伸缩特征上差异极大：预约受理是随营业时间波动的交互型负载，成本文件生成是夜间的计算密集型批量负载，而数据同步则是持续低频的事件型负载。如果采用单体部署，任何一种负载的峰值都会波及其他业务。第二，平台需要同时为 Java 内部服务、Go 周边平台与 PHP 既有系统三类调用方提供服务，接口定义一旦分散维护，字段口径必然随时间漂移，而这类问题往往在上线之后才暴露。第三，平台需要长期兼容基于旧版 AWS SDK 的既有代码，无法通过一次性重写来完成技术栈统一。下面分别论述我针对这三个挑战所做的设计与实现。

二、服务边界的划分与总体架构设计

服务边界的划分是微服务架构设计中最为关键的环节。我在划分时没有采用"按技术分层拆分"这种常见做法——因为按控制层、业务层、数据层拆分会导致一次业务请求穿越多个服务，反而放大调用开销与故障面——而是确立了三个划分维度。

第一，按伸缩特征拆分。我梳理了平台全部业务负载的伸缩曲线，将其归纳为三类：交互型负载（营业本部员工的预约受理与查询操作，呈工作日昼间高峰）、计算型负载（成本文件生成、邮件批量生成等定时作业，呈夜间定时峰值且瞬时资源占用大）、事件型负载（DynamoDB 数据变更触发的同步处理，持续低频）。据此，我把系统拆分为 Web、Service、Batch、FaaS 四类独立部署单元，使每一类都能按自身的伸缩曲线独立扩缩容。这一决策牺牲了单体部署时进程内调用的简单性，换来的是资源隔离与独立伸缩能力——在旅游业务的强季节性场景下，这个交换是值得的。

第二，按访问协议与调用方拆分。内部服务之间的调用我选择了 gRPC 而非 REST，主要基于三点考虑：gRPC 基于 HTTP/2 多路复用，在高频内部调用场景下连接利用率更高；采用二进制编码，序列化开销与报文体积更小；更重要的是，protobuf 天然提供强类型契约，这与我们后文将要论述的契约治理策略高度契合。对内对外则通过 Web 层暴露 REST 接口，兼顾浏览器友好性与前后端契约的稳定性。

第三，按数据存储特征拆分。这是我在此次设计中最为重视的一点。我采用混合存储策略：Aurora MySQL 承载需要事务与复杂关联查询的强一致交易数据，共 79 张表，其中主数据表 26 张（m_ 前缀）、业务表 53 张（t_ 前缀）；DynamoDB 承载字段演进频繁的半结构化数据，共 5 张领域表；S3 承载护照、文档、亲权同意书等文件实体。这样做的核心目的，是让服务边界与数据边界对齐——如果多个服务共享同一张表，那么无论代码上如何拆分，它们在数据层面依然是耦合的，任何一次表结构变更都会形成跨团队的连锁影响。

最终形成的架构是：Web 层承接交互请求，通过 gRPC 调用 Service 层的业务能力；Service 层访问 DynamoDB 与 S3；Batch 层承担夜间批量作业并通过独立数据源访问 MySQL；FaaS 层由 DynamoDB Stream 与消息队列驱动，负责跨存储的数据同步。

三、关键技术实现

契约驱动的服务通信。 针对多技术栈调用方的接口一致性问题，我在独立的规格模块中确立了以 protobuf 作为唯一契约源的策略。平台全部服务接口以 89 个 proto 文件定义，按职责分为服务定义、请求消息、响应消息、枚举与可复用消息类型五层组织——其中服务定义 1 个、请求与响应消息各 17 个、枚举 12 个、可复用消息 42 个。可复用消息层沉淀了错误信息、地址、旅行者、护照等被多个接口引用的公共结构，避免了同一结构在十几个接口中重复定义。在此基础上，我通过构建脚本编排了一条完整的生成链路：先由 protobuf 插件生成 Java 产物并发布至内部 Maven 仓库；再在容器化的 protoc 环境中生成 Go 产物并额外生成网关代码，发布为 Go 模块；随后生成 PHP 产物发布为 Composer 包；最后由 protoc 生成 OpenAPI 描述文件，经文档站点发布为在线接口文档。平台以单一服务对外提供 17 个远程调用接口，每个接口在契约中显式声明了统一的 HTTP 映射路径，三端口径由同一份契约保证一致。

服务端的统一分发设计。 服务端以单一入口类承接全部远程调用，未在每个接口上重复编写样板代码，而是通过统一的执行方法将请求分发到各业务实现类。这样设计的价值在于横切关注点的集中：日志记录、异常转换、调用上下文校验都可在分发层统一处理，各业务实现类只需关注业务逻辑本身。同时，我把被多个业务域共用的能力——文档、消息线程、亲权同意书、序列号、旅行信息——下沉为共享服务，避免同一逻辑在多个接口中重复实现。当然，单一入口在接口数量极大时会成为维护瓶颈，但以平台当前的接口规模而言，统一分发带来的收益明显大于其复杂度成本。

数据访问与批量处理。 关系型数据库侧统一采用 MyBatis 作为持久层框架，并纳入统一版本管理；NoSQL 侧通过增强客户端提供对象映射，通用操作封装在仓储基类中。批量作业方面，我为批处理配置了独立的读写数据源，通过包路径隔离数据访问接口：读取数据源指向 Aurora 的 cluster-ro 只读副本端点，写入数据源指向 cluster 主库端点，避免夜间批处理峰值挤占在线业务的连接资源。

四、实施中遇到的问题及解决措施

问题一：跨语言接口契约的一致性维护。 平台需同时服务 Java、Go、PHP 三类调用方，项目初期各端曾各自维护接口定义，导致同一字段在不同端的命名与类型出现差异，联调阶段才被发现。我的判断是，这类问题的根源不是开发人员疏忽，而是契约缺乏单一来源这一架构缺陷。因此我没有停留在逐处修正，而是把接口定义全部收敛到规格模块，使接口变更必须通过该模块提交；同时把三语言产物的生成纳入构建流水线，让接口不一致问题从"运行时联调发现"提前到"构建期暴露"。改造后，接口层面的联调返工显著减少。

问题二：依赖版本漂移引发的运行时故障。 平台初期各模块独立声明依赖版本，部分组件采用了动态版本区间。一次依赖升级后，protobuf 官方公共类型库被解析到一个候选版本，导致 gRPC 服务启动直接失败。这次故障让我意识到，我们虽然统一了业务接口的契约，却忽略了第三方依赖版本这一隐式契约。因此我建立了独立的统一版本管理插件，各模块通过插件接入统一的版本源，并对关键组件使用强制版本策略加以锁定。改造后，同一提交在任何机器上的构建产物完全一致，构建的可复现性得到保障。

问题三：跨存储的数据最终一致性。 混合存储带来了新的问题：写入主链路落在 DynamoDB，而报表与既有系统仍需从 MySQL 读取数据。若在服务端同步写两侧，主链路响应时间会被显著拉长。我的方案是把同步链路设计为事件驱动的无服务器架构：以 DynamoDB 数据流与消息队列作为事件源，驱动按业务域划分的十四个函数完成同步，主链路只写 DynamoDB 即返回。这一设计以最终一致性替代了强一致性——经评估，报表与通知场景可以接受秒级延迟，而预约写入等强一致场景仍走关系库事务，不做异步化。该方案使主链路响应时间由约 1.8 秒降至 420 毫秒。

五、总结与展望

平台上线至今已稳定运行约 8 个月，年可用率达到 99.95%，支撑业务量较原系统提升约 40%，接口一致性缺陷较改造前下降约 85%。回顾整个建设过程，我认为微服务架构在本项目的价值主要体现在三个方面：一是使业务特征差异极大的模块得以独立演进，批处理的资源峰值不再影响在线预约受理；二是通过契约的单一来源，让多技术栈协作从"人工对齐"变为"构建期保证"；三是使新增业务可以自然地落在最合适的存储与部署形态上。

当然，这一架构也带来了明显的代价。首先是分布式调试与问题定位的复杂度上升，一次跨服务请求的排查需要串联多个组件的日志；其次是跨服务的事务能力缺失，我们只能通过最终一致性来弥补；再次是运维单元增多，环境治理与监控的成本高于单体架构。

目前仍存在两点不足：一是跨语言契约虽有统一来源，但破坏性变更尚未实现自动化的兼容性检查，仍依赖人工评审；二是旧版云 SDK 与新版并存的过渡状态尚未终结，长期维护成本依然存在。后续计划引入契约兼容性校验工具，并逐步收敛 SDK 版本。

通过本项目，我深刻体会到微服务架构的价值并不在于"拆"本身，而在于让每个服务能够按照自身的业务节奏独立演进。架构师在面对微服务时，真正需要回答的问题不是"要不要拆"，而是"拆开之后，那些原本由进程内调用免费获得的确定性——事务、强类型、可调试性——要用什么来补回来"。
