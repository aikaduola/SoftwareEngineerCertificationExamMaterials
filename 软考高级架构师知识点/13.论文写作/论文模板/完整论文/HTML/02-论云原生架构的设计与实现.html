论云原生架构的设计与实现

云原生架构是基于云原生技术的一组架构原则和设计模式的集合，旨在将云应用中的非业务代码部分进行最大化的剥离，从而让云设施接管应用中原有的大量非功能特性，使业务不再有非功能性业务中断困扰的同时，具备轻量、敏捷、高度自动化的特点。云原生架构常用的技术包括容器、服务网格、微服务、无服务器计算等。

摘要

本文以我参与建设的 H.I.S. BASE HOME 旅游业务平台为例，论述了云原生架构在该项目中的设计与实现。该平台部署于 AWS 东京区域，承载预约管理、客户消息、通知发送与主数据联动等核心业务。我在项目中担任系统架构师，负责容器化方案设计、无服务器数据同步链路设计与交付流水线建设。针对数据同步与写入主链路相互耦合、计算单元粒度难以把握、云上配置与凭证治理复杂三大挑战，我从事件驱动解耦、按业务域划分计算单元、配置与凭证集中治理三个维度进行设计：以数据流与消息队列作为事件源，驱动按业务域划分的十四个函数完成跨存储同步，使写入主链路只需落到云数据库即可返回，达成秒级的最终一致性；每个函数拥有独立镜像、独立流水线与独立部署单元，实现故障域隔离。系统上线后运行稳定，写入主链路响应时间由约 1.8 秒降至 420 毫秒，平峰期计算成本下降约 35%，验证了方案的可行性。

正文

一、项目背景

H.I.S. 集团是日本大型旅游企业，其业务具有极强的季节性特征：长假前后预约量激增，平峰期则迅速回落。这种"峰谷差极大"的负载特征，使传统的固定容量部署方式陷入两难——若按旺季峰值配置资源，全年大部分时间资源闲置；若按平峰配置，旺季则无法支撑。

BASE HOME 平台于 2024 年 3 月启动建设，2025 年 1 月上线运行，服务集团 300 余家营业门店与约 5000 名业务人员，日均处理预约约 3 万笔、消息与通知约 12 万条。平台基于 Java 21 与 Spring Boot 3.5.7 构建，部署于 AWS 东京区域。

我在项目中担任系统架构师，主要负责三个方面的工作：一是容器化方案与运行基线设计；二是无服务器数据同步链路的设计；三是配置与凭证治理机制以及交付流水线的建设。

项目面临的三个核心挑战是：第一，平台采用混合存储，写入主链路落在云数据库（NoSQL），而报表与既有系统仍需从关系库读取数据，若在服务端同步写两侧，主链路响应时间将被显著拉长；第二，同步逻辑若作为一个整体部署，其扩容需求会绑架整个服务的资源配置，且一个业务域的故障会波及全部同步任务；第三，云上配置与访问凭证若散落在代码与配置文件中，既存在泄露风险，也会因环境差异导致"本地能跑、线上报错"。下面论述我针对这三点所做的设计。

二、云原生架构的总体设计

我把平台的云原生改造归纳为三个层次，自下而上依次是运行基座、计算形态与治理机制。

第一层是运行基座，即容器化交付。平台各模块分别构建独立镜像，统一基于集团提供的 Java 21 基础镜像，保证运行时基线一致；批处理模块不启用 Web 容器，仅作为短生命周期的计算进程运行，不占用端口，与在线业务在进程级完全隔离。

第二层是计算形态，即按负载特征选择容器或无服务器。我判断的标准是：负载是否持续、是否无状态、是否由事件驱动。在线交互与夜间批处理属于持续或定时负载，且需要稳定的运行环境，因此保留容器形态；而跨存储的数据同步属于持续低频、无状态、事件驱动的负载，非常适合无服务器形态，因此我将其设计为函数计算。

第三层是治理机制，包括配置管理、凭证管理与交付流水线。这一层最容易被忽视，却直接决定了云原生架构能否长期稳定运行。

无服务器同步链路的设计是本次改造的核心。我把同步链路拆解为四个部分：一是事件源，采用云数据库的数据流与消息队列，前者捕获数据变更事件，后者承接业务侧主动投递的消息；二是计算单元，即按业务域划分的十四个函数；三是配置源，全部配置与凭据统一存放于云参数服务，函数运行时按需读取；四是可观测能力，借助运行时框架提供结构化日志与链路追踪，并对消息队列的批量消费提供部分失败处理语义。基于这一设计，写入主链路只需将数据写入云数据库即可返回，同步由事件异步接管，两个关注点被彻底解耦。

三、关键技术的实现

按业务域划分函数粒度。 在划分计算单元时，我没有采用"一张数据表对应一个函数"的做法。理由是：同一业务域内的实体更新往往需要一起处理，例如旅行信息发生变更时，需要同步更新申请人与预约数据，若按表拆分，则一次业务变更会触发多个函数，函数之间还需要额外编排，反而增加了复杂度与不一致风险。因此我按业务域划分，使每个函数内部能够完成一次完整的业务处理。这一设计同时带来了故障域的隔离——某个业务域的处理异常不会波及其他业务域。目前十四个函数中，六个由消息队列触发，五个由数据流触发，三个由定时任务触发。

批量消费与部分失败处理。 函数消费消息队列或数据流时，一个批次中往往包含多条记录。若其中一条处理失败就导致整批重试，会造成大量重复处理。我借助运行时框架的批量处理工具实现了部分失败语义：消息队列侧按消息分组处理，只把失败分组中的记录返回给队列重试，正常分组照常提交；数据流侧同样只重试失败的记录。队列另配置了死信队列承接多次重试仍失败的记录。这一机制显著降低了重复处理的概率。

配置与凭证的集中治理。 我把全部配置与敏感凭据从代码和配置文件中剥离，统一存放在云参数服务中，函数运行时通过专用的客户端按需获取，代码仓库中不保留任何明文凭据。服务端侧同样遵循这一原则：不使用长期固定的访问密钥，而是通过安全令牌服务获取临时凭证，并配合默认凭证链兜底，使凭证自动轮换且有效期极短。此外，我通过云数据库表名统一携带环境前缀（开发 / 测试 / 验收 / 生产四套环境各有独立前缀）的方式实现了环境隔离，避免测试环境误连生产数据。

独立交付流水线。 每个函数拥有独立的镜像定义与独立的持续集成工作流，部署通过基础设施即代码工具完成。这带来的关键收益是：单个函数的变更不需要整体回归，支持单函数灰度与快速回滚。同时，容器化与本地云模拟工具的结合，使开发人员可以在本地拉起与云端一致的依赖服务（关系库用容器模拟、云数据库与对象存储用本地云模拟器模拟），消除了因环境差异导致的缺陷。

四、实施中遇到的问题及解决措施

问题一：同步链路的顺序性无法全局保证。 数据流能够保证同一分区内的事件有序，但跨分区不保证顺序。若两个业务域的数据存在先后依赖，并行处理可能产生顺序错乱，导致旧数据覆盖新数据。我的应对措施是：把存在依赖关系的实体收敛到同一分区键之下，例如旅行相关的各类数据统一以旅行编号作为分区键，借由分区内的有序性保证处理顺序；对于确实跨域的场景，则在数据中引入版本号，使乱序到达的更新可以通过比较版本号判定是否过期，从而避免覆盖。

问题二：消息推送的重复处理。 消息与邮件推送是本平台的可靠性敏感点，一旦重复发送，对客户而言是直接的体验事故，而朴素的失败重试必然会引入重复。我的方案分三层：第一层是以执行状态的幂等校验拒绝重复触发，从源头挡住重复；第二层是把重试能力独立为专用的重试服务，与业务逻辑解耦，使重试策略可独立调整而无需改动业务流程；第三层是投递状态跟踪表，逐条记录每一次投递的结果，使重跑时只处理未投递的记录，并在异常场景下可以精确定位漏发与重发的范围。改造后，重复发送率由改造前的约 0.3% 降至 0.01% 以下。

问题三：冷启动带来的延迟波动。 无服务器计算在低频函数上存在冷启动现象，首次调用延迟可达数秒。对于邮件生成等对延迟不敏感的场景，这一延迟可以接受；但对于由数据流触发的实时同步函数，则需要缓解。我采取的过渡措施是保留少量预热调用，并在后续规划中引入预置并发配置。需要说明的是，我并没有为此放弃无服务器方案——用函数形态换取弹性和按需计费，同时让部分延迟由业务侧的容忍度吸收，这个交换在本项目的负载特征下是合理的。

五、总结与展望

平台上线至今已稳定运行约 8 个月，年可用率达到 99.95%。云原生改造带来的收益主要体现在三个方面：一是写入主链路响应时间由约 1.8 秒降至 420 毫秒，用户体验明显改善；二是十四个函数按业务域独立扩缩容，任一函数故障不再波及其他业务域；三是按需计费的计价方式使平峰期计算成本下降约 35%，缓解了旅游淡旺季资源利用率失衡的问题。

同时，这一架构也带来了不可忽视的代价。首先是无服务器形态下的调试困难，本地难以完整复现云上的触发链路；其次是函数之间的依赖关系不像进程内调用那样直观，跨函数的数据流向需要额外维护文档；再次是链路追踪的复杂度上升，一次数据同步可能横跨数据库、事件源与多个函数，排查问题需要串联多方日志。

目前仍存在两点不足：一是跨存储的同步链路尚无统一的延迟监控，异常时的排查路径偏长；二是冷启动在低频函数上仍有可感知延迟。后续计划补充一致性延迟监控与预置并发配置，并逐步把函数间的依赖关系显式化。

通过本项目，我认识到云原生架构并非普适的解决方案。它真正适合的是事件驱动、无状态、负载突发型的场景；而对于强一致的事务处理、长时间运行的计算任务以及负载长期稳定的服务，传统的容器化部署仍是更稳妥的选择。架构师的职责，正是准确判断哪一部分负载属于前者、哪一部分属于后者。
